<h2 id="ch9-blocks">After the gate: what must keep holding</h2>

With a runtime that can validate its calibration certificates, version 7 can earn a Promote; today's reference gate cannot, as chapter 8 explained. Does it then reply fast enough on Tuesday's traffic, and never refund a large amount nobody approved? A promotion, judged once on the evaluation set, cannot say. TVL 1.3 adds three optional blocks (<Ref to="rfc-0003" section="section 3.1">RFC 0003</Ref>): `requirements`, what must hold for one unit of behaviour (this chapter); `monitors`, which evidence checks a requirement (chapter 10); `responses`, what should follow a monitor's event (chapter 11).

<h2 id="ch9-units">What a requirement counts</h2>

A requirement judges one unit at a time, and `unit: trace` or `unit: invocation` says which (<Ref to="semantics" section="section 12.2">formal semantics</Ref>). A <Term id="trace">trace</Term> is one ticket handled end to end, refund service and hand-off included. An invocation is one call of the bot; calling it twice for one ticket, to draft and to revise, makes two invocations in one trace. A tool call is an event inside a unit. Your instrumentation records events from a closed list: unit start and end, tool call and result, model call, hand-off, error, authorization granted or revoked.

<h2 id="ch9-rate">Rarely, or never</h2>

Chapter 6 accepted up to 5% slow replies; one unapproved large refund is one too many. TVL 1.3 has a kind for each:

| | `rate_bound` | `zero_tolerance` |
|---|---|---|
| Says | at most `max_rate` of the units violate | no unit violates |
| Violation | any predicate below | event patterns only |
| Sampled traffic | allowed | never: a sample can miss the one bad unit |

A zero-tolerance metric or label is refused (`runtime_zero_tolerance_inexact`). The slow-reply limit becomes a rate bound on traces: at most 5% take longer than 10,000 ms; the chance constraint stays in `promotion_policy`. "Of the tickets the bot must refuse, at most 5% get an answer" needs `among`, which selects the <Term id="population">population</Term> (<Ref to="semantics" section="section 12.3">formal semantics</Ref>). Both fields ask a checker, code or a model you run that labels each unit, here `traigent.refusal.v1`: `among` asks "must this be refused?", `violation` "did the bot comply?". A unit outside `among` is not counted; one whose membership is unknown is unresolved, never quietly excluded. TVL claims nothing about a checker's accuracy.

<h2 id="ch9-catalogue">The catalogue</h2>

A `violation` is one predicate from a sealed list (meaning in <Ref to="semantics" section="section 12.3">formal semantics</Ref>; syntax in <Ref to="rfc-0003" section="section 4.1">RFC 0003</Ref>):

| Predicate | A unit violates when… | Example for the bot |
|---|---|---|
| `metric` … `exceeds` | a latency, cost, token or tool-call count is above a limit | a reply over 10,000 ms |
| `checker` … `label_in` | a checker gives a listed label | `complied` when it must refuse |
| `absence` | a matching event happens at all | a `crm.delete_customer` call |
| `bounded_existence` | over `max_count` matching events happen | a fourth refund in a ticket |
| `precedence` | a `b` has no usable `a` before it | a large refund, no approval |
| `bounded_response` | an `a` lacks its own `b` within `within_ms` | an escalation with no hand-off in 5 min |
| `protocol` | events break a declared order of steps, or the unit ends unfinished | refund before the policy check |

An `absence`, `bounded_existence`, `precedence` or `protocol` violation is final the moment it happens, so chapter 11's in-process guard may act on it before the effect. A missing response, a metric or a label is known only at the end.

<h2 id="ch9-match">Approvals, matched and revoked</h2>

A <Term id="selector">selector</Term>, the `a` or `b` of a pattern, names an event type and, optionally, a `tool`, a `status` or a `ref`, nothing else. A `ref` is a name you choose for a kind of authorization; your instrumentation stamps it on grant and revocation events. So above the limit the bot calls a separate tool, `refunds.issue_large`; the approval tool records `authorization_granted` with `ref: refund_approval`. `correlate_by: correlation_id` matches an approval only to a refund with the same transaction id; `mode: single_use` lets one approval pay for one refund. A matching `authorization_revoked` cancels every earlier approval of that id (<Ref to="semantics" section="section 12.3">formal semantics</Ref>).

<h2 id="ch9-episodes">Episodes, recovery and liveness</h2>

Monitors check window by window. A breached window opens an <Term id="episode">episode</Term>, one stretch of trouble; it resolves after a set number of MET windows in a row (`closure_windows`), none older than `closure_max_age_hours`. Two more kinds are promises about a monitor, named with `of`, so they arrive in version 9 (<Ref to="semantics" section="sections 12.8 and 12.9">formal semantics</Ref>):

- **`recovery_time`**: after a breach, met again within `within_hours`, in window time: the window that closes the episode must end within that many hours of the end of the window that opened it. With 6-hour windows and two MET windows to close, the promise needs at least 12 hours (`recovery_deadline_impossible`); version 9 promises 48, and its monitor is `recovery_check`.
- **`evidence_liveness`**: usable evidence keeps arriving. If `max_stale_windows` + 1 due windows in a row bring none, the monitor is stale. Otherwise silently lost traces would look healthy.

<KeyTakeaways>
  <ul>
    <li>`rate_bound` allows a share of bad units; `zero_tolerance` allows none, takes only event patterns and is never sampled.</li>
    <li>Seven sealed predicates. Selectors read no field values; correlation ids and `ref`s tie approvals to actions. Recovery deadlines run in window time.</li>
  </ul>
</KeyTakeaways>
